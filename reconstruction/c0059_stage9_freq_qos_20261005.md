# Candidate0059 Stage9 policy-scoped FREQ_QOS control

Stage8 proved that the pinned Lisa 5.4 baseline no longer supports the donor
`CPUFREQ_ADJUST` contract and that CPU-frequency limits must be expressed as
frequency QoS requests.

Stage9 is the bounded migration of that path. It adds one FREQ_QOS MIN request
and one FREQ_QOS MAX request to each cpufreq policy and owns their lifetime from
`CPUFREQ_CREATE_POLICY` through `CPUFREQ_REMOVE_POLICY`. Existing policies are
attached during `migt_init`, so late registration does not silently miss the
policies created earlier in boot.

The requests are neutral by default:
- MIN = `FREQ_QOS_MIN_DEFAULT_VALUE`
- MAX = `FREQ_QOS_MAX_DEFAULT_VALUE`

Legacy-style `migt_freq` and `migt_ceiling_freq` module parameters provide
per-CPU requested values. A non-zero `boost_policy` enables the bounded boost
path. QUEUE_BUFFER temporarily applies the configured MIN floor and re-arms a
short clear timer. SET_CEILING arms a per-UID MAX cap and a bounded clear timer.
If no frequency is configured for a policy, that policy keeps the neutral QoS
value.

The policy value is clamped to that policy's hardware cpuinfo range before it is
submitted. The implementation does not write `policy->min`/`policy->max`
directly, does not use `CPUFREQ_ADJUST`, does not call `core_ctl_set_boost`, and
does not disable or replace thermal constraints. Thermal and other FREQ_QOS
clients therefore continue to participate in the cpufreq aggregate.

This stage deliberately does **not** claim exact donor timing, core-control
boost, GLK policy, Metis compatibility, Android runtime success, or a jank fix.
Those remain separate gates. A Stage9 PASS proves source semantics plus affected
object compilation against the exact pinned Lisa source.
