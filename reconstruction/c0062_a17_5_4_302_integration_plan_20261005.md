# Candidate0062 integrated HyperOS 4 / Android 17 plan

Prepared: 2026-10-05

## Goal

Candidate0062 is the first integrated target intended to combine:
- the proven Candidate0059 Lisa functionality,
- a semantically audited Linux 5.4.302 stable base from Candidate0061,
- the Candidate0060 Android17/BPF compatibility overlay.

Candidate0062 is NOT created by merging arbitrary donor snapshots.

## Dependency chain

1. Candidate0059
   - 5.4.289 verified reference
   - Wi-Fi/battery/UFS ownership and ABI work
   - MIGT/package-runtime/FREQ_QOS
   - BPF ringbuf Stage-A
2. Candidate0061
   - pure official linux-stable v5.4.289 -> v5.4.302 uplift
   - preserves Candidate0059 gates
3. Candidate0060 overlay
   - MiYume-vs-official-v5.4.302 donor extraction
   - broader BPF5.10 compatibility required by Android17
   - close_range/CLOSE_RANGE_CLOEXEC where required
   - CAP_PERFMON/CAP_BPF/CAP_CHECKPOINT_RESTORE and SELinux capability2 mapping
4. Candidate0062
   - compile, static/ABI/identity/packaging verification
   - HyperOS4/Android17 device validation

## Why 5.4.302 comes first

MiYume is a 5.4.302 tree. Using a Lisa 5.4.302 source as the feature-port base gives a clean comparison:

official Linux v5.4.302
-> MiYume 5.4.302 donor-specific delta
-> filtered BPF/Android17 compatibility patch
-> Lisa 5.4.302

This is cleaner than:
Lisa 5.4.289 -> MiYume 5.4.302
because that comparison mixes the full official stable uplift with donor features.

The checked official BPF core is unchanged between 5.4.289 and 5.4.302, so the BPF5.10 backport is still required. Shared files such as net/core/filter.c and fs/file.c do receive stable changes, which is why applying the feature overlay after the stable uplift is safer.

## Candidate0060 patch extraction rule

For every Candidate0060 file:
1. compare official v5.4.302 to MiYume pinned 6f0290557329655f29c9b1bc52eec33e36f859ba;
2. classify each hunk as:
   - generic BPF5.10 dependency,
   - Android17 compatibility,
   - Xiaomi/Qualcomm adaptation,
   - unrelated donor customization;
3. only the first three classes may be considered;
4. unrelated donor customization is excluded.

Explicit exclusions:
- SELinux permissive/androidboot.selinux hacks
- ReSukiSU/KernelSU/SuSFS
- F2FS tuning unrelated to Android17 boot
- SM8350 device DTS/drivers
- mitigation disabling
- global frequency locks or thermal bypass
- fake device/ioctl/property success

## BPF/A17 staging

Stage A:
- preserve Candidate0059 ringbuf support
- normalize the code against the 5.4.302 base
- verify no regression

Stage B:
- BPF link API / iterator prerequisites
- verifier/helper/UAPI dependencies
- BTF parser/runtime dependencies required by the selected programs

Stage C:
- trampoline/dispatcher/tracing/ext/sk_lookup only where Android17 loader evidence requires them
- struct_ops/LSM/local storage only where dependency or real loader evidence requires them

Stage D:
- Android17 syscall/capability compatibility
- close_range(436)+CLOSE_RANGE_CLOEXEC
- CAP_PERFMON=38
- CAP_BPF=39
- CAP_CHECKPOINT_RESTORE=40
- capability2 SELinux class mapping

Do not enable every donor feature merely to claim parity.

## Developer Options

Developer Options remains a separate acceptance axis.

Current evidence points to an external property override/resetprop style source for the bad 1/1/0/0 tuple, not a proven kernel-source defect.

Candidate0062 must therefore:
- retain enforcing SELinux;
- keep release property semantics;
- use the prepared provenance/repair collector;
- require post-device 0/0/1/1 property state;
- require Settings Developer Options to open without logpersistd fatal/denial.

Do not represent a device-side property/module repair as a Linux 5.4.302 or BPF patch.

## Static gates before boot packaging

Require all inherited Candidate0059 gates plus:
- Makefile reports 5.4.302
- official stable provenance complete
- no unresolved Candidate0061 conflict entries
- BPF overlay changed-file inventory complete
- no excluded MiYume customization
- vmlinux/System.map confirms required BPF objects/symbols
- syscall 436 maps to close_range without breaking Lisa process_madvise=440
- cap_last_cap expected value is explicit
- CFI and MODVERSIONS stay enabled
- stock msm_drm 736-import ABI remains valid
- module_layout CRC gate passes
- battery/UFS/Wi-Fi/camera/HWID/flash ownership gates pass
- fixed-region boot and AVB gates pass

## Device gates

First Android17/HyperOS4 boot capture should check:
- init reaches userspace
- bpfloader success/failure details
- netd and TrafficController
- BPF_MAP_CREATE/BPF_PROG_LOAD/BPF_LINK_CREATE errors
- unknown helper/map/prog/link types
- close_range behavior during netd helper spawn
- /proc/sys/kernel/cap_last_cap
- Wi-Fi and tethering
- battery/charging
- display/GPU
- MIGT/FREQ_QOS
- Developer Options
- SELinux enforcing
- no sustained crash/reboot/vibration loop

## Naming / truthfulness

Do not call a build Candidate0062 VERIFIED until:
- Candidate0061 stable uplift is statically proven,
