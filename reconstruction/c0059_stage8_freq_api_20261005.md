# Candidate0059 Stage8 CPU-frequency API map

Stage7 restored the bounded legacy `migt` device and real QUEUE/DEQUEUE render
tracking, but deliberately left frequency ceiling and boost inactive.

The public same-generation donor cannot be copied directly for the next step.
Its MIGT frequency path depends on the old `CPUFREQ_ADJUST` policy-notifier
contract.  The exact pinned Lisa baseline no longer exposes
`CPUFREQ_ADJUST`; it exposes only policy CREATE/REMOVE notifications and uses
`struct freq_constraints` plus `freq_qos_add_request()`,
`freq_qos_update_request()`, and `freq_qos_remove_request()` for policy
limits.

Therefore the next bounded port must translate donor min/max frequency requests
to policy-scoped FREQ_QOS MIN/MAX requests.  It must attach requests to each
unique cpufreq policy, handle policy create/remove lifetime, preserve thermal
and other QoS constraints, and never pin maximum frequency globally.

The exact Lisa baseline still exposes `core_ctl_set_boost()`, but Stage8 does
not activate it.  Core-control boost and GLK frequency policy remain separate
later gates because they have additional lifetime and thermal implications.

A Stage8 audit PASS means the API migration direction is proven against the
exact Lisa source.  It is not a frequency-policy implementation, Android16
runtime proof, or a jank fix.
