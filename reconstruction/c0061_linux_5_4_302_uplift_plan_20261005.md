## Why MiYume is useful but cannot be copied wholesale

MiYume proves a Xiaomi Qualcomm 5.4 vendor tree can be carried to 5.4.302 while also supporting newer Android userspace, but its tree includes changes outside official 5.4.y stable:
- Linux 5.10-era BPF backports
- Android17 close_range/CLOSE_RANGE_CLOEXEC adaptation
- CAP_PERFMON/CAP_BPF/CAP_CHECKPOINT_RESTORE
- ReSukiSU / SuSFS
- F2FS tuning
- device-specific SM8350 drivers and defconfigs
- historical SELinux permissive/androidboot.selinux hacks

Candidate0061 must therefore use official 5.4.y stable as the version source of truth.
MiYume is used only to identify vendor-conflict resolutions and Xiaomi/Qualcomm adaptation patterns.

## Upgrade method

1. Fetch official linux-stable tags v5.4.289 and v5.4.302.
2. Generate the cumulative official 5.4.289 -> 5.4.302 patch/file inventory.
3. Compare that changed-file set against the Lisa vendor divergence from upstream v5.4.289.
4. Treat the intersection as the conflict-risk set.
5. Compare the same sensitive files against MiYume 5.4.302 for vendor adaptation hints.
6. Port official stable changes semantically into the Lisa vendor tree.
7. Never resolve a conflict by replacing an entire Qualcomm/Xiaomi file with MiYume.
8. Preserve Android KABI reserves, QGKI modversions and current vendor module ownership.
9. Build after bounded batches, not only once after all 13 releases.
10. Only change reported kernel version to 5.4.302 when the full stable delta has been audited/applied.

## Android17 items that are NOT automatically provided by 5.4.302

Official 5.4.302 alone does not imply the MiYume Android17 compatibility surface.

Lisa 5.4.289 baseline currently has:
- CAP_LAST_CAP=37
- no close_range syscall at 436
- process_madvise at 440
- only the older BPF core plus Candidate0059 ringbuf Stage-A

MiYume additionally has:
- CAP_PERFMON=38
- CAP_BPF=39
- CAP_CHECKPOINT_RESTORE=40

- much broader Linux5.10 BPF backport

Those are tracked under Candidate0060 and must not be mislabeled as part of stable 5.4.302.

## Qualcomm-specific stable changes already identified

Official 5.4.y changelogs contain several Qualcomm fixes directly relevant to Lisa's historical boot/power/firmware problem space:

- 5.4.291:
  - clk: qcom: clk-rpmh integer-overflow fix; this path is tied to RPMh/IPA clock calculation.
  - clk: qcom: clk-alpha-pll alpha configuration fix.
- 5.4.296:
  - pinctrl: qcom: msm marks interrupt-invalid pins, including UFS-reset style GPIO cases.
- 5.4.297:
  - soc: qcom: mdt_loader adds stricter ELF-header bounds validation.
  - usb: dwc3: qcom avoids leaving BCR asserted after probe/deferral failure.
- 5.4.300:
  - soc: qcom: mdt_loader handles zero e_shentsize/e_shnum firmware correctly after the stricter 5.4.297 validation.
  - dmaengine: qcom: bam_dma fixes DT error handling that could otherwise depend on firmware/timing and cause early boot crashes.
- 5.4.301:
  - remoteproc: qcom: q6v5 fixes double disable of the handover IRQ.
  - soc: qcom: rpmh-rsc always clears TCS_AMC_MODE_TRIGGER to prevent false completion IRQs around deeper low-power modes.
- 5.4.302:
  - remoteproc: qcom: q6v5 prevents duplicate handover handling and reference-count damage to power domains/clocks/regulators.
  - soc: qcom: smem fixes endian handling of num_entries.

These changes are not assumed compatible merely because they are upstream stable.
They must be checked against Lisa's downstream Qualcomm implementations before application.

Priority note:
- mdt_loader and q6v5 changes are especially relevant because this Lisa project previously investigated PAS/firmware reset behavior.
- rpmh-rsc / clk-rpmh changes are high priority because they can affect power-domain and clock sequencing.
- dwc3/qcom and pinctrl/UFS-reset changes are device-runtime correctness fixes and should not be dropped accidentally during conflict resolution.

## Integration decision: uplift before Android17/BPF overlay

The Candidate0060/Candidate0061 ordering was re-evaluated against official Linux v5.4.289/v5.4.302 and the pinned MiYume 5.4.302 donor.

Checked official files that are byte-identical between v5.4.289 and v5.4.302 include:
- kernel/bpf/Makefile
- kernel/bpf/btf.c
- kernel/bpf/syscall.c
- kernel/bpf/verifier.c
- kernel/bpf/helpers.c
- include/linux/bpf.h
- include/linux/bpf_types.h
- include/uapi/linux/bpf.h
- include/uapi/linux/capability.h
- include/uapi/asm-generic/unistd.h
- arch/arm64/include/asm/unistd32.h
- include/linux/fdtable.h
- kernel/sys.c
- security/selinux/include/classmap.h

Checked shared dependencies that DO change during the stable uplift include:
- net/core/filter.c
- fs/file.c

Therefore 5.4.302 does not remove the need for the Linux5.10 BPF/Android17 backport, but it is a cleaner integration base because:
1. the donor itself is 5.4.302;
2. donor-vs-official-5.4.302 cleanly isolates feature/vendor deltas;
3. stable fixes to shared dependencies are already present before BPF/A17 patch adaptation;
4. the final feature port avoids being rebased again across the 289->302 stable delta.

Final ordering:
Candidate0059 (5.4.289 verified reference)
-> Candidate0061 (pure official stable uplift to 5.4.302)
-> Candidate0060 compatibility overlay
-> Candidate0062 integrated build/device validation.

## 2026-10-05 execution policy update: combine uplift work with touch stabilization

The implementation strategy is revised based on the active HyperOS 3.0.9 / Android16 device baseline and Candidate0059 User B touch regression.

Candidate0061 may now implement:
- official Linux 5.4.289 -> 5.4.302 stable uplift;
- Candidate0059 touch-latency corrections that are required because the uplift touches overlapping scheduler/cpufreq/vendor-sensitive code.

This is an implementation-stream merge, not an evidence merge.

Every change must still be classified and gated separately:

### Stable-only class
Examples:
- official 5.4.290..5.4.302 fixes
- Qualcomm stable fixes such as q6v5/mdt_loader/rpmh/dwc3/bam_dma
- generic scheduler/cpufreq/mm/fs/net stable changes

Required evidence:
- exact official stable provenance
- vendor conflict resolution note
- compile/modpost/ABI result

### Touch/performance class
Examples:
- package-runtime/WALT hot-path semantic corrections
- restoring donor-equivalent deferred history roll behavior
- restoring a safe pause/enable semantic if required
- reducing avoidable shared user-state writes from the scheduler hot path
- adapting FREQ_QOS interaction only if A/B evidence implicates it

Required evidence:
- direct relation to Candidate0059 User B regression
- same HyperOS 3.0.9 Android16 workload/control
- Goodix IRQ/InputDispatcher/TouchFeature evidence
- no loss of Candidate0059 jank improvement

### Mixed-conflict class
If an official 5.4.302 stable patch and a touch/performance correction touch the
same file, resolve them in this order:
1. establish the official 5.4.302 semantic state;
2. re-apply the minimal touch/performance correction on top;
3. record both provenances;
4. test the stable gate and touch gate independently.

Do not solve conflicts by copying entire MiYume files.
